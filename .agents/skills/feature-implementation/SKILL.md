# Feature implementation

1. Read the issue, acceptance criteria, relevant `AGENTS.md` files and existing code.
2. Identify affected crates, APIs, UI and compatibility requirements.
3. Implement the smallest complete solution using existing patterns.
4. Cover intended behaviour and important failure cases with tests.
5. Update documentation when public behaviour or configuration changes.
6. Run relevant checks and verify each acceptance criterion.

## Engineering rules

- Respect crate boundaries, authentication, durability and resource limits.
- Avoid unrelated refactors, new dependencies and speculative abstractions.
- Do not claim unrun tests passed or conceal known limitations.

## Final response

Report the changes, acceptance criteria, checks actually run and outstanding risks.
Always include a **ready-to-paste pull request description** in Markdown, even when no PR was opened:

- **Summary:** What the change achieves and why.
- **Changes:** The main implementation details and affected areas.
- **Validation:** Tests and checks run; explicitly identify anything not run.
- **Notes:** Compatibility, operational impact or outstanding risks, if any.
- **Issue:** Link the relevant issue; use `Closes #N` only when fully resolved.

Write the PR description in a natural maintainer voice. Do not include agent/AI attribution,
"generated by" disclaimers, co-author trailers, or commentary about the implementation agent.
Keep it concise, factual and suitable for direct use on GitHub.
