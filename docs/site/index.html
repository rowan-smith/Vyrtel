Features

The whole stack in one process.

Logs, traces and metrics share one store, one UI and one query language.

Logs

Structured search that stays fast

Query any field, nested paths included. Live tail, a filter panel built from your data, and exceptions with stack traces.

Send logs →

OpenTelemetry

Standard in

Any SDK or Collector over OTLP/HTTP, protobuf or JSON.

Connect →

Traces

Waterfall and related logs

See which span was slow or failed, and jump between logs and traces.

Metrics

Counters, gauges, histograms

Aggregate and group by any attribute over any time range.

Dashboards

Panels on a grid

Log counts, metric lines, single stats and saved queries side by side.

Alerts

Thresholds with webhooks

Get notified when log counts cross a threshold, with state history.

Storage

Crash-safe by design

A write-ahead log, compressed segments, and indexes that let queries skip most of the data.

Operations

Simple to run

Per-signal retention, API keys, health checks and a non-root image.

Ask production a question.

# slow requests

# level ranges and grouping
level >= Warning and (service = "orders" or service = "payments")

Get started

Running in one command.

Start the binary, open the URL it prints, and send events over OTLP or plain HTTP.

  • Point OpenTelemetry at OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:8080
  • Or POST JSON / NDJSON to /api/v1/events
  • Everything persistent lives in one directory

Why Vyrtel

Observability shouldn't need more resources than the software it observes.

A typical stack

  • Search cluster for logs
  • Time-series database for metrics
  • Tracing backend + its storage
  • Message queue in front of it all
  • Dashboards and alerting service

Several services, several gigabytes of RAM, before the first log line.

→

Vyrtel

HTTP API · OTLP ingestion · query engine · storage · metadata · web UI · background jobs

One process and one data directory.
